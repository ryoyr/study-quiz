# Study Quiz 4.6.0 要件定義

## 1. 目的

LPIC-1 Exam 101の学習を、通信断やサーバー停止に依存せずブラウザー内で継続できるローカルファーストPWAとして提供する。問題管理、3方式の回答、適応型出題、復習、分析、バックアップ、任意のAI補助を一つのアプリで扱う。

## 2. 利用者・前提

- 主利用者: 個人学習者
- ビルド: Node.js 20.19以上、npm
- 利用: Chrome/Chromium系を主対象
- 既定公開パス: `/study-quiz/`
- 認証、複数端末同期、サーバー正本は現行範囲外

## 3. 機能要件

### FR-01 初回設定

試験日、出題上限、新規上限、バッファ率、即答判定秒数、非学習日、既定の学習範囲・理解度・出題方法、テーマを設定できること。

### FR-02 問題管理

- 登録、編集、検索、絞込、アーカイブ、復元ができること。
- 問題IDは一意であること。
- 回答方式は`single`、`multiple`、`text`の3種とすること。
- `questionType`のない旧問題は`single`とすること。
- 入力上限はID 200文字、カテゴリ／サブカテゴリ／タグ各500文字、長文20,000文字、タグ30件、選択肢8件、入力許容回答100件とすること。
- 同一内容の選択肢を重複登録できないこと。

### FR-03 回答定義・採点

- 択一: 1件の正解インデックスと一致すること。
- 複数選択: 順序に依存しない正解集合の完全一致とすること。
- 入力: NFKC、前後空白除去、連続空白集約、英字大小無視後の完全一致とすること。
- 永続化の旧互換フィールドを各機能が直接解釈せず、方式別の内部回答定義を介して採点・表示・外部連携すること。

### FR-04 CSV

- UTF-8（BOMあり／なし）、引用符、改行を扱えること。
- 共通必須列は`id, category, text`とすること。
- 旧択一CSVを継続読込みできること。
- 複数選択は`answers`、入力は`acceptedAnswers`を`|`区切りで指定できること。
- 重複ID、範囲外回答、方式固有必須値不足、入力上限超過を行単位で表示すること。

### FR-05 学習セッション

試験枠、範囲、理解度、出題方法、個別問題から重複のないセッションを生成し、中断・再開できること。アーカイブ済み問題を通常出題から除外すること。

### FR-06 履歴・復習・分析

- 回答日時、方式別回答、正誤、時間、即答スコア、FSRS評価を保存すること。
- 新規履歴は回答時点の`answerType`を保持すること。旧履歴は方式なしでも読めること。
- 新規履歴は回答時点の問題文・方式・回答表示・正答表示を任意スナップショットとして保持すること。
- 履歴画面はスナップショットを優先し、後日の問題編集・削除で過去表示を変更しないこと。旧履歴は現行問題から表示すること。
- 統計、弱点、忘却候補、進捗予測、間違いノート、お気に入りへ反映すること。

### FR-07 教材・AI補助

- AI質問文は3方式の回答定義と利用者回答を正しく表現すること。
- 類似問題生成は3方式それぞれのJSON契約を提示・検証・編集できること。
- 一括ファクトチェックは3方式を判別できる回答定義を出力すること。
- 外部送信は利用者の明示操作でのみ実行すること。

### FR-08 保存

- 通常データはlocalStorage、初回設定の互換領域はIndexedDBも利用すること。
- 関連更新はジャーナル、ロールバック、読戻し検証を行うこと。
- 複数タブ競合を検知し、古い状態からの上書きを防止すること。

### FR-09 完全バックアップ

- version 2～9を読込み、version 9を出力すること。
- FNV-1aチェックサムで偶発破損を検知すること。
- 復元前に形式、参照、差分を検証し、安全バックアップ後にだけ復元すること。
- APIキー、内部状態、廃止キーを含めないこと。
- 3方式の問題・履歴を損失なく扱うこと。

### FR-10 PWA

インストール、オフライン起動、更新通知、ショートカット、Apple Touch Icon、通常／maskableアイコンを提供すること。キャッシュ保存やNavigation Preload失敗時にフォールバックすること。

### FR-11 問題・解説品質向上

- 問題データを方式別回答定義を含むJSONとして出力できること。
- ファクトチェックと同じコピー方式で、問題文・選択肢・正答・解説の修正提案と補足提案をJSONで取り込めること。
- 提案登録と問題適用を分離し、変更前・提案後・状態をレビューできること。
- 提案作成後に問題が変更された場合は上書きを停止すること。
- 適用時は問題と提案状態を同一トランザクションで更新すること。
- 適用済み内容を初期データ更新JSONとして出力し、検証ツールで新規環境の初期問題へ反映できること。

## 4. 非機能要件

### NFR-01 互換性

- アプリ: 4.6.0
- localStorage schema: 9
- IndexedDB version: 2
- 完全バックアップ: version 10、version 2～10読込み
- 既存キー、旧`answerIndex`、旧`selectedIndex`を維持

### NFR-02 品質

`npm run check`で構成検証、単体試験、TypeScript build、Chrome E2Eを順に実行すること。環境制約はソース不良と分離して報告すること。

### NFR-03 アクセシビリティ

320px幅、キーボード、フォーカス可視化・復帰、Escape取消、読み上げ、forced-colors、reduced-motion、テーマコントラストを考慮すること。

### NFR-04 セキュリティ・プライバシー

HTML直接挿入、動的コード実行、認証情報同梱を行わないこと。Gemini APIキーを完全バックアップへ含めないこと。FNV-1aが電子署名ではないことを明示すること。

## 4.7.0 問題マスターGitHub連携要件

- 配布元問題を現行`Question`形式のmanifest／dataset JSONで管理する。
- 問題ID、端末保存、回答履歴、FSRS、バックアップ互換を維持する。
- 端末編集と配布元更新を区別し、競合を自動上書きしない。
- GitHub送信前に追加・更新・アーカイブとフィールド前後値を表示する。
- 利用者が明示確定した場合だけWorkersへ送信する。
- WorkersはAccess JWT、許可利用者、Origin、Rate Limit、入力、対象datasetを検証する。
- GitHub App秘密情報はWorkers Secretsにのみ保存する。
- リポジトリ、main、`public/content`はWorkers設定で固定し、クライアント指定を受け付けない。
- 変更は専用ブランチの1コミットとし、mainへ直接コミット・自動マージしない。
- version／問題フィンガープリント競合時は409で停止する。
- 同一内容の再送でコミット・PRを重複させない。
- PR URLとopen／closed／mergedを画面表示する。
- マージ後の問題マスターはnetwork-firstで取得し、失敗時は既存問題・キャッシュを維持する。
